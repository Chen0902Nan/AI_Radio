# 网易云音乐开放平台：个人路线是否可行

日期：2026-09-15
用途：为 [Q23 确认表](q23-confirmation.md) 第 13 条（音乐接入最终采用哪条线）补齐事实依据。
方法：只读官方文档站，未登录、未提交任何申请、未创建应用。

## 实测结果（2026-09-15，拿到真实 appId 后）

用真实 appId + privateKey 自建了一个只读探针（`scripts/openapi-probe.mjs`），不经过 CLI：
按官方「应用签名」规则拼待签串（剔除 sign 与空值、按 key 的 ASCII 升序、`k=v&…`、SHA256withRSA）并调用官方接口。

**待签串里没有 appSecret**，只要 appId + privateKey；签名格式被服务端接受。

### 接口能力矩阵（同一张匿名 accessToken）

| 接口 | code | 含义 |
| --- | --- | --- |
| 查询歌曲（搜索） | 301 | 用户未授权当前接口 |
| 获取歌单详情 | 301 | 用户未授权当前接口 |
| 获取歌曲详情 | 301 | 用户未授权当前接口 |
| 获取用户基本信息 | 301 | 用户未授权当前接口 |
| 获取热搜榜 | 300 | 应用未授权当前接口 |
| 批量获取歌曲信息 | 300 | 应用未授权当前接口 |
| **获取歌曲播放url** | **300** | **应用未授权当前接口** |
| **批量获取歌曲播放url** | **300** | **应用未授权当前接口** |

这是同一张令牌、同一套设备参数下的对照实验，结论很干净：

- **301 的接口说明应用是已授权的**，只是缺用户登录 —— 搜索、歌单、歌曲详情、用户信息都属于这一类，登录后应该能用。
- **300 的接口是应用层级就没有权限**，换成用户令牌也不会变。**取播放地址的两个接口都在这一类。**
- 匿名登录本身正常：`code=200`，能拿到 86400 秒有效期的 accessToken。

### 设备参数也不是自助的

`device` 里的 `channel` / `deviceType` / `os` 文档写明“由云音乐分配，需线下联系云音乐同事确认”。
本机 `ncm-cli` 实际发送的是 `channel=ncmcli`、`os=ncmcli`、`brand=ncmcli`、`deviceType=openapi`。
也就是说：**官方 CLI 之所以能用，是因为它带着一个被授权的通道身份**，而不是因为 appId 本身拿到了这些权限。

## 这对本项目的结论

1. **个人入驻拿到的不是一套可自助接入的 API，而是“用官方 CLI”的资格。**
2. 自建播放器要的取音源接口，在个人应用下是应用层级未授权（300），文档里多处写着开通需线下联系。
3. 厂商路线虽然能谈，但明确“仅支持企业入驻”且“音乐服务不是免费提供”，与个人自用项目不匹配。
4. 因此：**播放器继续用现有社区接口，不迁移到官方开放平台。** 资料读取、搜索、歌单这些如果将来想走官方，登录后是可行的（301 类），但取音源不行，而取音源正是播放器的命脉。

这个取舍已沉淀为 [ADR-0002](../../docs/adr/0002-music-source-unofficial-api.md)。

## 未验证的部分

- 上述矩阵用的是**匿名** accessToken。按错误语义，300 是应用级授权缺失，换用户令牌不会改变；但确实没有用真实用户令牌复测过。
- 没有实际去走用户扫码登录（需要你本人操作），所以“301 类接口登录后可用”是根据错误语义推断，不是实测。
- 平台控制台上的“应用详情”到底有没有显示每日剩余次数、有没有开通取音源接口的入口，没去看。

## 安全事项

探测过程中私钥被粘进了对话，已经落在了聊天记录里。**建议到开放平台重新生成一次 privateKey**（appId 不用换）。
本机副本在 `data/openapi-cred.json`（已 gitignore、权限 0600），不再需要时可以删。

## 结论摘要

开放平台有**两条互斥的入驻路线**，个人项目走的是「个人接入」这条：

| | 个人接入 | 厂商接入 |
| --- | --- | --- |
| 主体 | 成年实名用户 | **仅支持企业，不支持个人开发者** |
| 费用 | 文档未提任何费用 | 明确写「本平台音乐服务不是免费提供」 |
| 审核 | 填信息提交，**符合条件即会被通过** | 需公司信息与业务描述，3~5 个工作日评估 |
| 额度 | 每人当天接口调用次数有上限，具体数字只在应用详情里显示 | 按合作协议 |

另有一条硬限制：**同一用户只能选择一个身份类型入驻**，已作为厂商入驻的账号无法再以个人身份入驻。

官方确实提供取音源接口，所以「官方 CLI 拿不到网页音源」这个判断不是接口层面的，只是 CLI 没有把它作为公开子命令暴露。

## 官方取音源接口

「音乐API文档 > 获取播放地址API」下有三个接口：

| 接口 | 路径 |
| --- | --- |
| 获取歌曲播放url | `/openapi/music/basic/song/playurl/get/v2` |
| 批量获取歌曲播放url | 同族批量版本 |
| 获取歌曲无法播放toast文案 | 同族 |

「获取歌曲播放url」返回 `url`、`size`、`md5`、`br`、`level`、`freeTrail`（试听起止时间）。`bitrate` 默认 320，无损（999）与 Hi-Res（1999）需要联系云音乐同事单独开通高品质服务。

**权限边界写得很明确**，用 subcode 区分：

| subcode | 含义 |
| --- | --- |
| 200 | 正常返回播放 url |
| 10002 | 获取版权错误 |
| 10003 | 因合作方要求，请前往手机端收听（当前端无版权） |
| 10004 | 该歌曲为付费歌曲，请前往手机端购买后收听 |
| 10005 | 未知错误 |

也就是说：**能拿到什么取决于账号本身的权益**，付费歌曲不会因为接了开放平台就变免费。这与本项目「只使用账号有权播放的内容」的边界一致。

另外几项实测/接入前需要知道的约束：

- **全曲试听**：平台针对 appid 管控 `playflag`；试听场景下 `playflag` 可默认置 true。需要透传 `openApiTraceInfo`，`auditionStart/auditionEnd` 是试听起止时间，**用于版权结算，不是用户真实播放时长**。
- **限流**：以 AppID 的各个接口为单位限流，调用频率超过阈值 **50** 会返回 -444 / -445 / -446。
- **地址有效期**：音频时长小于 25 分钟时为 25 分钟；大于 25 分钟时为音频时长。车载、电视、手表、音箱端是 1 天。
- **公共参数需要 `accessToken`**，即仍然需要用户扫码授权，不是有 appId 就能直接取任意歌曲。
- 平台有两个 CLI 侧 FAQ 结论：`ncm-cli` **不支持下载**、不支持笔记。

## 没查到的（文档层面无法确认）

这三条只能靠实际入驻后才能知道，不能凭文档推断：

1. **个人 appid 能否调用 `playurl` 系列接口**。文档没有按 appid 类型区分接口权限，而 `playflag` 又是「针对 appid 管控」的，个人应用的实际开放范围未知。
2. **每人每天调用次数的上限具体是多少**。文档只说「有上限，见应用详情」，没有公开数值。对每天要读几百首歌、每小时取一次播放地址的电台来说，这个数字是不是够用完全未知。
3. **是否需要额外的资质或协议**。文档只写了实名成年这一个条件。

## 对当前项目的影响

- 本项目是**个人自用**，不是要发布给别人的产品。个人接入路线的定位（成年实名个人、本机 CLI 听歌）与这个用途吻合；厂商路线反而进不去（不支持个人开发者）。
- 我们现在跑通的是社区维护的 `@neteasecloudmusicapienhanced/api`，两条路线的接口能力其实高度重合（都是取播放地址 + 试听/付费标记），主要差别在**稳定性和合规性**：官方有文档合同与限流约定，社区接口随时可能被改协议或封掉。
- 迁移成本不高：音乐接入已经收敛在 `server/netease.js` 一层，换成官方接口主要是替换「取播放地址」和「资料读取」两组调用，加一套签名 + accessToken 授权流程。
- 风险点是**额度**。个人路线的每日调用上限没有公开数字，如果太小，反而不如现在。

## 建议

值得花一次实名申请去试——免费、自助、符合条件即通过，拿到 appId 后第一件事就是实测三件事：能否调 `playurl`、拿到的地址是不是完整歌曲、每天额度够不够。这三件事决定了它能不能替代现有方案。

但**不建议现在就切换**。当前链路已经跑通并验证过，先按社区接口继续开发不阻塞；等个人入驻批下来实测完再决定要不要迁移，是成本更低的做法。
