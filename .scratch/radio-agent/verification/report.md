# 第一阶段验证报告：音乐资料 → 完整歌曲 → 本地网页播放

日期：2026-09-14（修订：2026-09-15 补充代码审查修复与回归）
范围：只验证「读取本人网易云音乐资料」「获取有权播放的完整歌曲」「本地网页播放」，含下一首与单曲失败换歌。不含 DJ、TTS、天气、飞书日历、聊天、每日调度。
结论：**链路打通，14 项浏览器检查全部通过**。官方网易云 CLI 路线因缺少开放平台凭据受阻，本轮改用参考方案里的音乐 API 方向。完整产品仍未实施、未验收。
后续代码审查又发现了三个缺陷，已修复并补了能稳定复现的回归验证（见第 7 节）。

## 1. 采用的接入方案及版本

| 组件 | 版本 / 位置 | 用途 |
| --- | --- | --- |
| Node.js | v24.16.0 | 运行时 |
| `@neteasecloudmusicapienhanced/api` | 4.40.1（项目内 `node_modules`） | 网易云数据读取与音源查询 |
| `@music163/ncm-cli`（官方） | 0.1.7（项目内安装，未使用） | 仅用于核实接入前提 |
| `puppeteer-core` | 25.11.0（devDependency） | 驱动系统 Chrome 做真实浏览器验证 |
| Google Chrome | 152.0.7977.83（headless=new，系统安装版） | 真实播放验证 |
| 系统 | macOS 26.6.2 (arm64) | — |

**为什么不是官方 CLI。** 官方 `@music163/ncm-cli@0.1.7` 已在本机安装并核查：未配置凭据时任何命令（含 `--help`）都直接退出；用临时 HOME 写入假凭据后，`--help` 与 `commands` 只列出静态命令（play/pause/state/login/tui/configure 等），**`search`、`playlist`、`user favorite` 等资料命令来自远端动态 manifest，必须有有效的开放平台 appId + privateKey 才会注册**。凭据来自网易云音乐开放平台个人入驻，本机没有。另外该 CLI 的播放由 mpv 承担，不能用来验证网页播放；也没有找到稳定公开、无播放副作用的取音源命令。

**因此采用 API 方向，边界明确：**
- 只用标准只读接口：`/api/song/like/get`、`/api/v3/song/detail`、`/api/user/playlist`、`/api/v6/playlist/detail`、`/api/song/enhance/player/url/v1`、登录相关接口。
- **不传 `unblock` / `match` 参数，不启用任何额外音源**，只返回当前账号本身有权播放的内容。
- 登录用手机扫码（`ncm-cli` 之外的独立流程），cookie 只写本机 `data/session.json`（权限 0600），前端永远拿不到 cookie，也拿不到带鉴权参数的 CDN 直链（音频经本服务转发）。
- 额外副作用说明：首次运行会向网易注册一个**匿名设备 token** 用于辅助查询，这不修改用户的红心、歌单或任何音乐数据。账号内没有任何写操作。

本轮验证使用的账号：`Pluto_Magic`，uid `1734543760`（VIP）。

### 分页检查（有实测发现）

- 红心歌曲 `/api/song/like/get` **一次返回全部 id，没有服务端分页**；歌曲详情按 300 条分块请求（456 条 → 2 块）。


## 7. 修复记录：代码审查发现的缺陷

审查证据：`.scratch/radio-agent/verification/artifacts/fixes-regression.json`（18 项检查全通过）

### 第一轮：A/B/C/D

### 缺陷 A／B：播放控制竞态（`public/app.js`）

- **现象**：快速连续点下一首时，先发出的解析请求可能后返回，把用户最后选中的歌覆盖掉，播放器实际放的是旧的那首；解析过程中点暂停，晚到的解析结果又会把播放重新拉起来。
- **原因**：`playIndex` 只按 `await` 顺序落结果，没有"这次结果还属不属于当前意图"的概念；暂停也没有取消在途请求的途径。
- **修复**：引入播放意图代次号 `playToken`（每次播放/暂停/切歌自增）和 `userWantsPlayback`。异步结果回来时代次不匹配就直接丢弃；暂停会自增代次作废所有在途请求。解析期间按钮显示"暂停"，让用户有取消入口；失败退避定时器也会检查用户是否已经暂停，不再复活播放。

### 缺陷 C：音源缓存不随身份和权限变化失效（`server/netease.js`）

- **现象**：刷新确认某曲已不可播放、或退出登录后，仍可能命中旧缓存里的播放地址。
- **原因**：`resolveTrack` 先查缓存再确认会话，缓存条目也不绑定身份；且只在"有地址"时写缓存，没地址时不清除旧条目。
- **修复**：缓存条目绑定身份（cookie 截断哈希，不保存明文）；查询前先确定身份，身份不匹配直接作废；地址有效则写缓存，无地址/不可播放则删除旧条目；登录与退出登录时整体清空缓存。响应里增加 `identityKind`（user/anon）便于观察。

### 缺陷 D：资料读取脚本会误报成功（`scripts/read-library.mjs`）

- **现象**：资料缺失、分页不一致或部分歌单查询失败时，报告里虽然写了，但脚本仍以 0 退出，只看退出码会把失败当成功。
- **原因**：判定逻辑散在流程里，只有"未登录"一处分了退出码。
- **修复**：判定逻辑抽到 `scripts/lib/library-checks.mjs` 的 `collectFailures()`，统一检查红心去重与详情缺失、分页一致性、歌单完整性与重复、音源查询报错、各步骤成败；失败时写进报告并 `process.exitCode = 1`。

### 第二轮：P1/P2/P3（播放控制的残留问题）

- **P1 暂停后恢复播错歌**：切歌加载中暂停，再点播放会恢复上一首，但界面显示的是新歌。根因是按钮的恢复分支只看 `audio.currentTime > 0`，没有检查播放器里装的是不是列表当前这首。修正：新增 `loadedSrcId()`，只有已加载的音频就是列表当前曲目时才直接续播，否则重新按当前曲目播放。
- **P2 旧定时器切走用户选择**：某首歌失败后会排一个 1.2s 的自动换歌定时器；若用户在这段时间里手动选了别的歌，定时器仍会触发并把它切走。修正：失败时记住当时的 `playToken`，定时器触发时代次变化就说明用户已有新意图，不再执行。
- **P3 暂停后自动出声**：用户暂停之后到达的媒体错误，会在地址刷新成功后自动播放。修正：`refreshCurrent()` 仍会刷新地址，但只在 `userWantsPlayback` 为真时才 `play()`；暂停期间只换地址不出声。错误处理里也区分了"暂停时到达的错误"和"播放中断"。

### 回归验证（`npm run verify:fixes`）

| 检查 | 方法 | 结果 |
| --- | --- | --- |
| A 快速切歌不被旧请求覆盖 | 用请求拦截让先发出的解析请求最晚返回（1600/800/0ms），断言最终 `audioSrc` 与 `currentId` 一致 | 通过 |
| B 加载中暂停不被拉起 | 人为拖慢解析 1.8s，加载中点暂停，等迟到结果返回 | 通过 |
| P1 加载中暂停后恢复播对歌 | 切歌加载中暂停→再点播放，断言播放器实际地址等于界面当前曲目 | 通过 |
| P2 定时器不切走手动选歌 | 注入失败后手动选另一首，越过 1.2s 退避再断言仍是手动选的那首 | 通过 |
| P3 暂停期间媒体错误不出声 | 注入音频流 502 并让元素重发真实请求，断言仍为暂停、但地址已刷新 | 通过 |
| C 刷新确认不可播放后清缓存 | 注入"刷新返回不可播放"，再普通查询，断言 `cached=false` | 通过 |
| D 退出登录后不复用旧身份缓存 | 临时备份会话文件→退出登录→断言 `identityKind=anon` 且 `cached=false`→恢复会话 | 通过 |
| E 判定逻辑与退出码 | 9 组合成报告的判定自检 + 真实让脚本进入失败分支检查退出码 | 通过（退出码 2） |

**测试有效性（敏感性）验证**：把 `public/app.js`、`server/netease.js` 的修复临时回退到修复前的版本，A/B/P1/P2/P3 与 C 均稳定失败（实测两轮都验证过）；恢复修复后全部通过。这排除了"测试永远通过"的可能。

测试设计上踩过并修正的坑：

- 注入点原先自己删缓存，属于自己验证自己。现在注入只替换上游返回值，分类与缓存处理走正常路径。
- 竞态原先靠网络抖动碰巧触发，改为确定的延迟序列。
- 触发"暂停期间的媒体错误"时，先用了 `audio.load()`，但 Chrome 会用媒体缓存直接回应、根本不发网络请求，错误也就不会发生；而且 `preload="none"` 时改了 src 也不会去拉。现改为显式允许预加载并对同一首歌发一次真实请求，并用一条独立断言确认确实出现过 502（否则上一条可能空过）。

## 8. Codex 选歌最小验证

证据文件：`.scratch/radio-agent/verification/artifacts/codex-plan.json`（13 项检查全通过）

### 接入方式

| 项 | 值 |
| --- | --- |
| CLI | `codex-cli 0.153.4`（/Applications/ChatGPT.app/Contents/Resources/codex） |
| 认证 | 复用本机已登录的 ChatGPT/Codex 订阅，未使用 API key |
| 调用参数 | `codex exec -C <空目录> --skip-git-repo-check --sandbox read-only --ephemeral --ignore-user-config --color never --output-schema <schema> -o <out> <prompt>` |
| 结构化输出 | JSON Schema 约束 `{picks:[{id,reason}]}`，从 `-o` 读最终消息，不解析事件流 |
| 默认超时 | 90s，超时直接 SIGKILL 子进程 |

参数选择上的实测对比：不加 `--ignore-user-config` 时会加载用户的 skills 上下文（约 2.7 万 token 且有截断警告）；加上之后降到约 2.1～2.3 万 token，认证不受影响（认证走 CODEX_HOME，与 config.toml 无关）。**每次调用约 2 万 token**，这是订阅额度上的实际开销，接入编排层时需要控制调用频率。

### 真实调用结果

- 单次调用：exit code 0，耗时 12.4～13.1s，22,711 tokens（含提示词中的 60 首候选）。
- 输入：从 456 首红心歌曲随机抽 60 首作候选，加一句收听场景描述。

### 结果校验（模型输出当不可信输入）

- **id 必须在候选集里**：编造的 id 直接丢弃并记录原因。
- **不能重复、必须有理由**：缺理由或重复的条目丢弃。
- **可播性二次校验**：模型给的 id 只是候选，进入队列前逐个用真实账号查音源，不可完整播放的降级丢弃；全部不可播则整体回退。
- **部分非法时保留合法部分**：实测注入“编造 id + 真实 id”混合输出，返回 `ok:true` 且 `kept=2、rejected=2`，被拒项都带原因。
- **全部非法**：判为 `invalid_output`，不进入队列。

### 浏览器验证

- Codex 选歌接入队列时**没有打断正在播放的歌曲**：接入前后 `currentId` 不变、仍处于播放状态。
- 队列结构：原曲留在队首，Codex 选出的 5 首接在其后。
- 界面上逐首显示中文选歌理由，队列里的曲目带 Codex 标记。
- 点 Codex 选出的第一首（`喜欢` — 陈奕迅，id 326719，时长 279.93s）**在网页里真实播放**。

### 失败续播

三种失败都通过测试注入制造，并对**同一个固定基线**断言（避免前一个用例破坏状态后，后面的“未变化”变成空过）：

| 失败类型 | 结果 |
| --- | --- |
| timeout | 队列与选歌结果均未变化、当前曲目未变、仍在播放（进度继续推进 2.81s），界面显示“继续使用原队列，播放不受影响” |
| quota | 同上 |
| invalid_output | 同上，提示具体是“2 条全部不合法” |

### 敏感性验证

把两处临时改坏：(a) 失败分支里清空队列；(b) 去掉“id 必须在候选集里”的校验。结果：校验逻辑自检、部分非法处理、以及三种失败续播共 5 项检查全部稳定失败；恢复后 13 项全通过。

### 未验证 / 限制

- 只验证了“红心歌曲内部选歌”，规格中的 70/30 探索比例、喜好反馈权重、避免短时重复都未实现。
- 未接 DJ 串场、天气、日历、每日调度。
- 真实超时/额度不足未从真实 Codex 侧触发（会消耗订阅额度或需要等真实限流），用的是可控注入；真实的 codex 失败分类（退出码与 stderr 文本）只做了代码实现，未用真实失败样本验证。
- 选歌质量没有量化评估，只有单次样本的目视合理性。
- 每次约 2 万 token，未做长时高频调用的额度影响评估。
