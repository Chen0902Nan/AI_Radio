# 探索选歌开发访谈

日期：2026-09-18。

## 目标与已确认边界

- 用户要求完成探索选歌开发，并调用 grill-with-docs 进行需求访谈及文档记录。
- 默认目标为约 50% 红心、收藏或自建歌单内歌曲、50% 歌单外探索；不要求每批严格配比。
- 下方历史问答保留当时的 30/70 表述；比例统一以 2026-09-18 最新修订的 50/50 为准。
- 探索歌曲沿用 CONTEXT.md：根据音乐口味选出的歌单外歌曲，不保证从未听过，也不限近期发行。
- 明确点歌优先于比例；候选不足或服务受限时优先继续播放可播歌曲，并显示原因。
- 下一首不改变长期偏好；喜欢/不喜欢保存在本地，不写回网易云。
- 保留 ADR-0002 的音乐接入方式与 ADR-0003 的浏览器队列归属。
- 沿用既有访谈记录中用户每次只回答一个问题的偏好。

## 决策树

1. 探索体验：贴近既有口味的程度 → 候选来源及排序。
2. 曲库边界：红心、收藏与自建歌单的范围 → 歌单内外分类及读取不完整时的处理。
3. 生效范围：首次开播、主动选歌、自动补歌、手动歌单 → 比例统计口径及跨批平衡。
4. 重复与反馈：已听探索曲、不同版本、负反馈 → 去重、降权与恢复行为。
5. 验收：真实探索来源、可播性、比例与退化路径 → 本地回归及真实链路证据。

现有实现和本地音乐接入能力由只读代码核查补充，不要求用户回答可从代码获得的事实。

## Q1：探索离现有口味多远（已确认 B）

场景：红心和收藏以华语民谣、独立流行为主。探索可主要选择相近风格，也可包含少量不同语言或曲风，或经常明显跨风格。

建议：以相近口味为主，穿插少量不同歌手、语言或曲风；不额外规定一个僵硬的内部比例。

用户回答：B。以相近口味为主，偶尔穿插不同语言或曲风。

## 代码核查

- `apps/web/src/features/library/Library.tsx:25-35`：首载将全部红心歌曲放入队列；手动选择歌单同样替换整个队列。
- `apps/web/src/features/player/Player.tsx:21-38`：开播只建立会话并恢复播放，不请求智能选歌。因此只修改补歌不能保证从开播起获得探索体验。
- 手动 Codex 选歌与自动补歌目前都只读取红心候选；音乐接入层已支持读取收藏、自建歌单及其曲目。
- 本地安装的音乐 API 有每日推荐、私人 FM、相似歌曲和搜索模块；本轮没有调用真实接口，可用性仍待验证。

## Q2：默认开播是否直接进入混合电台（已确认 A）

建议：普通开播从第一批就按 30% 歌单内、70% 探索准备；用户主动选择某个歌单时仍按该歌单播放。比例不要求每批严格达到，准备不自动出声。

备选：保留默认开播直接播放红心，仅在主动点击 Codex 选歌或后台补歌时启用混合选歌。

用户回答：A。普通开播从第一批就加入探索歌曲；主动选择某个歌单时仍播放该歌单。等待准备及歌单播完后的续播规则留待后续确认。

## Q3：歌单内歌曲是否包含自建歌单（已确认 A）

当前领域定义为已接入的红心或收藏歌单中的歌曲；接口另能读取用户自建歌单。

建议：将红心、收藏歌单和自建歌单的歌曲合并为歌单内范围；探索歌曲必须在这个范围之外。同一平台歌曲只计一次。

备选：保持红心和收藏歌单范围，自建歌单不纳入，因此其中未红心、未出现在收藏歌单的歌曲可以作为探索歌曲。

用户回答：A。红心、收藏歌单和自建歌单共同构成歌单内范围，探索从该范围之外寻找。已同步 CONTEXT.md 的歌单内歌曲定义。

## Q4：首次混合选歌尚未准备好时如何开播（已确认 B）

背景：默认开播改为混合电台后，读取歌单、获取探索候选及 Codex 选歌可能需要等待。

建议：点击开播后优先播放一首已确认可播的歌单内歌曲，后台准备混合队列，准备完成后接在当前歌曲之后；首曲计入自动选歌的歌单内份额，不打断当前歌曲。暂停或停止后，迟到的准备结果不得触发出声。

备选：等待混合首批准备好才开始播放，期间显示准备进度，允许取消。

用户回答：B。点击开播后等待混合首批就绪才出声，期间显示正在准备。首批准备失败时的提示、重试与是否降级另行确认，不把失败当作混合首批就绪。

## Q5：探索候选如何发现（已确认 A）

本地代码事实：Codex 当前只能从服务端提供的真实歌曲候选中选择；已安装音乐 API 存在推荐、相似歌曲、搜索模块，但真实接口可用性仍待验证。

建议：结合网易云推荐和相似歌曲获取候选，排除全部歌单内歌曲，再由 Codex 按用户口味与当前氛围筛选。优先复用现有真实候选校验机制。

备选：同时允许 Codex 主动提出歌手或歌曲，再用网易云搜索确认具体歌曲与完整可播音源；需要处理同名、版本及不存在的歌曲，模型建议本身不能直接入队。

用户回答：A。第一版结合网易云推荐和相似歌曲提供候选，排除歌单内歌曲，再由 Codex 按音乐口味和当前氛围挑选。不增加 Codex 自主提名后搜索找歌的路径；真实接口可用性由开发验证。

## Q6：手动歌单播完后如何续播（已确认 A）

已确认手动选择歌单时按该歌单播放，不在其中强插探索歌曲；原规格要求用户不主动停止时持续续播。

建议：手动歌单播完后自动接回 30% 歌单内、70% 探索的混合电台。手动选择的歌单曲目不计入自动选歌比例，避免播完一长份歌单后为了追补比例而连续只播探索。

备选：继续在该歌单内循环，直到用户主动切回混合电台。

用户回答：A。手动歌单播完后自动接回混合电台，手动播放的歌单曲目不计入自动选歌比例。

## Q7：自动选歌比例按哪个范围累计（已确认 B）

已确认不要求每批严格配比。需要明确短批次之间如何平衡，以及停止后重新开播是否继承前次偏差。

建议：按一次收听会话内实际首次出声的自动歌曲数量累计；正常候选充足时逐步接近 30/70，排队但未播、手动歌曲与 DJ 均不计数。暂停继续沿用，停止后重新开播重新累计；跳过不撤销已出声歌曲的计数，也不改变长期偏好。准备后续批次时同时考虑尚未播放的自动歌曲，避免反复补偿同一偏差。

备选：跨收听会话累计，让每天只短听几首时也能逐步接近 30/70；前次比例偏差会影响下次开播的选歌。

用户回答：B。按实际开始播放的自动歌曲数量跨收听会话累计，前次探索偏少时后续适当增加探索。手动歌曲和 DJ 不计入，每批不要求严格配比。不得采用上方建议中的停止后清零规则。累计的时间范围及服务降级后如何避免长期追补，仍待明确。

## Q8：首次开播时探索不可用如何处理（已确认 A）

场景：用户已点击开播并等待准备，但探索接口不可用或没有足够的完整可播探索歌曲；歌单内仍有可播歌曲。区分本题的已失败状态与 Q4 的仍在正常准备状态。

建议：明确显示探索暂不可用，本次先用可播的歌单内歌曲开播，后续恢复混合选歌；不假称已满足探索比例，不无限等待或重试。

备选：首次开播不自动降级，显示失败并提供重试及“先听歌单内歌曲”选择；已经开始收听后的故障仍按原规格优先续播。

用户回答：A。首次探索准备失败时，明确提示后自动使用可播的歌单内歌曲开播，恢复后再加入探索。不将仍在正常准备中的等待直接当作失败。

## Q9：跨次累计看多长的历史（已确认 A）

依赖：Q7 选择跨会话累计，Q8 允许探索失败时降级播放歌单内歌曲。需避免过去长期故障形成无限的探索比例追补。

建议：看最近 50 首实际开始播放的自动歌曲，跨停止、重开及应用重启保存；手动歌曲、DJ 不计入。降级歌曲按实际类别计入，但恢复后逐步调整，不为了补旧比例而连续只播探索。最近窗口之外的偏差不再影响当前选歌。

备选：从启用功能起累计全部自动歌曲；长期总比例更接近目标，但很久以前的偏差仍会影响当前选歌。

用户回答：A。以最近 50 首实际开始播放的自动歌曲作为滚动统计范围，跨次收听保留；新的播放记录进入后，最早的记录退出统计。手动歌曲与 DJ 不计入，更早的偏差不再影响选歌，不要求每批严格达到 30/70。

## Q10：多久可以再次自动推荐同一首歌（已确认 A）

依赖：Q9 已确定最近 50 首自动歌曲的统计范围。本题单独确认重复推荐规则，不把比例统计窗口自动当作去重规则。

建议 A：尽量避开最近 50 首实际开始播放的自动歌曲，跨次收听生效；可播候选不足时允许提前重复并提示，明确点歌不受限制。

备选 B：只在本次收听中尽量避免重复，停止后重新开播可以再次自动推荐此前歌曲；可播候选不足时同样允许重复并提示，明确点歌不受限制。

用户回答：A。自动选歌尽量避开最近 50 首实际开始播放的自动歌曲，跨次收听生效；可播候选不足时允许提前重复并提示，明确点歌不受限制。这是另行确认的重复推荐规则，不改变 Q9 的比例统计口径。

## Q11：同一首歌的不同版本是否也算重复（已确认 A）

依赖：Q10 已确认跨次收听避开近期歌曲。本题只确认重复推荐的识别范围，不改变歌单内外分类或喜好反馈范围。

选项 A：只避开听过的具体版本；同一歌手同一首歌的现场版、重录版或另一专辑版本仍可推荐。

建议 B：同一歌手、同一首歌的不同版本也尽量避开；其他歌手翻唱仍可作为不同歌曲推荐。避免仅通过更换版本反复推荐同一首歌，版本识别存在歧义时不保证完全去重。

用户回答：A。近期重复推荐只避开实际听过的具体版本；同一歌手同一首歌的现场版、重录版或另一专辑版本仍可推荐。不采用建议 B 的跨版本合并规则，也不据此扩大喜好反馈的作用范围。

## Q12：标记“不喜欢”后如何影响自动推荐（已确认 A）

已确认显式喜好反馈长期保存于本地，跳过不改变长期偏好，不写回网易云；本题确认“不喜欢”的排除强度。

建议 A：不再自动推荐这个具体版本，直到用户撤销“不喜欢”；候选不足也不自动放回，仍允许用户明确手动点播，不连带屏蔽其他版本或歌手。

备选 B：降低这个具体版本被自动推荐的机会，但以后仍可能出现；不连带屏蔽其他版本或歌手。

用户回答：A。被标记“不喜欢”的具体版本不再自动推荐，直到撤销；候选不足也不自动放回，仍允许用户明确手动点播，不连带排除其他版本或歌手。该明确排除优先于 Q10 的候选不足时允许重复规则。

## Q13：标记“喜欢”后，优先找相似歌曲还是也增加原歌重播（已确认 A）

依赖：已确认以探索为主、近期防重复及本地显式反馈；本题确认正向反馈如何影响自动选歌。

建议 A：主要用于寻找相似、合口味的探索歌曲；原歌仍按普通选歌规则安排，不因喜欢而额外提高重播机会。

备选 B：既用于寻找相似歌曲，也提高这个具体版本再次被选中的机会；仍遵守最近 50 首的防重复规则。

两种方案均保留 30/70 默认比例目标及歌单内外定义，不自动写回网易云。

用户回答：A。喜欢主要用于寻找相似、合口味的探索歌曲，原歌仍按普通规则安排，不额外增加原歌的重播机会。保留已确认的比例目标、近期防重复和歌单内外定义，不写回网易云。

## Q14：歌单资料读取不完整时如何处理探索（已确认 A）

场景：部分红心、收藏或自建歌单未能读取，且没有可用的完整歌单记录，因此无法可靠确认候选是否在所有歌单之外。已确认的探索定义不允许把未知归属直接算成歌单外。

建议 A：暂不加入新的探索候选，先用已确认的可播歌单内歌曲续播，并提示歌单资料未读完整；读取恢复后再恢复探索，不把缺失资料当作空歌单。

备选 B：允许继续加入推荐歌曲，但明确标记归属尚未确认，不声称它们属于歌单外探索；其比例统计方式需在选择 B 后进一步确认。

用户回答：A。资料读取不完整且没有可用的完整歌单记录时，暂缓新增探索候选，先播放已确认的可播歌单内歌曲并提示原因；读取恢复后继续探索，不把未读到的资料视作空歌单。
