# 编排层：队列留在网页端，服务端只负责准备下一批

自动补歌需要协调「队列、生成、播放意图、失败恢复」，但播放器只有一个网页 `<audio>`，且浏览器要求用户手势才能出声。决定：**播放队列与播放意图代次留在网页端（`public/orchestrator.js` + `public/app.js`），服务端 `server/orchestrator.js` 只负责准备下一批可播内容**，不把队列搬到服务端，也不新增第二套播放调度。

服务端的职责被限制为：按会话与意图代次去重生成、调用 Codex、做可播性二次校验、失败时降级用曲库候选、给 Codex 记退避冷却、以及让已经停止的会话结果作废。网页端的职责是：决定何时补歌、只追加不替换、按代次丢弃迟到结果、暂停不出声、队列末尾等待下一批。

## Considered Options

- **服务端持有队列并推送播放指令**：单一事实来源，但浏览器手势、`<audio>` 状态、失败重试都要跨进程来回，等于重做一遍已通过验证的播放器竞态处理；本轮范围不需要。
- **整个补歌逻辑都放网页端**：实现最少，但多标签页或页面重连会重复生成同一批，且停止后的结果只能靠客户端自觉丢弃，缺少服务端兜底。
- **客户端队列 + 服务端协调（采用）**：改动面最小，复用既有播放意图代次机制；三层去重（客户端在途标志、服务端 sessionId+epoch Promise 复用、结果 id 去重）保证不会重复生成；服务端 `invalidateSession` 给停止会话兜底。

## Consequences

- 队列不是服务端持久状态：网页刷新后不恢复队列，需要重新开播；这符合规格「刷新不自动出声、不创建重复播放任务」。
- 若将来要支持多设备接续收听，需要把队列提升为服务端状态，届时网页端控制器可退化为纯渲染层。
- 队列条目统一带 `type` 字段；当前只有 `track`，非 track 类型会被明确跳过并提示未实现，为后续「歌曲与播报统一编排」保留位置，但不把未实现能力写成已完成。
- 补歌的去重范围与发送给服务端的排除范围必须是同一个集合（当前曲＋待播＋已失败），不含已播历史：否则完整曲库播到末尾时，服务端返回的候选会被前端全部过滤成「补充 0 首」然后停止。已播曲目可以重新入队，短时间重复靠 45 分钟降权缓解，而不是靠过滤。
- 默认参数（阈值 2、批量 5、退避 30s→5min、Codex 冷却 1→15min）按真实 Codex 的 ~15s／~2.28 万 token 与 3～5 分钟歌曲时长选取，细节见 [验证报告第 10 节](../../.scratch/radio-agent/verification/report.md)。
