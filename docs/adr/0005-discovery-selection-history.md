# 探索比例按实际播放统计，模型只负责口味排序

默认 50% 歌单内、50% 探索。如果按生成批次计数，用户跳过、停止或手动点歌后会产生不存在的“收听历史”；如果让模型自行保证比例或归属，结果又无法稳定验证。

决定：服务端读取红心、收藏与自建歌单的完整并集，再从平台推荐和相似歌曲取得探索候选。模型只在真实候选中排序。归属、完整可播音源、反馈排除与比例由应用控制。无法证明曲库完整且没有可用完整记录时，暂缓探索；失败不是空歌单。

每个准备结果携带服务端登记的 selectionId，绑定歌曲与当次归属。浏览器收到首次实际 playing 时提交 playInstanceId；SQLite 按实例幂等记账。手动点播不携带自动来源标识，DJ 不走歌曲记录。旧记录归属未知，保留原记录但不补造比例。最近 50 条自动歌曲跨会话/重启保留。

近期重复是可以在可播候选不足时放宽的规则，不喜欢是直到撤销才解除的硬排除；均按平台歌曲版本 ID 判断。喜欢用于相似探索种子，不加大原歌重播概率。

继续沿用 ADR-0003 的浏览器队列与意图归属。初次点击开播先准备混合批次；暂停、停止、换歌单会使迟到结果失效。手动歌单播完后追加自动批次。音源探测次数有上限，探索与歌单内兜底分别计时，探索超时不能挤占全部兜底机会。

## 替代方案

- 按排队数量计数：队列可能从未播放，不能表示实际收听。
- 让模型自行分类并满足固定配额：模型无完整平台归属证据，且试听/不可播会破坏配比。
- 永久屏蔽全部历史歌曲：有限候选会耗尽队列。只对具体版本的不喜欢做硬排除。

## 影响

新增 `plays` 可空来源/实例字段与 `selections` 表，兼容原 SQLite 数据。来源在准备时固定，后续歌单变化不回写历史。曲库完整记录按账号缓存；没有缓存的进程重启需要重新读取。真实服务与本地模拟验证分别记录，见 [验收记录](../../.scratch/discovery-selection/verification.md)。
